# Requirements Document

## Introduction

The RAG Health & Fitness Engine is a full-stack web application that provides personalized fitness and nutrition recommendations through conversational search. The system combines vector search over exercise and recipe databases with large language model generation to create weekly health plans tailored to user demographics and goals.

## Glossary

- **System**: The RAG Health & Fitness Engine web application
- **User**: A person accessing the application to receive fitness and nutrition recommendations
- **Vector_Store**: Elasticsearch 8.x instance storing exercise and recipe embeddings
- **Embedding_Model**: all-MiniLM-L6-v2 model running via @xenova/transformers
- **LLM**: Google Gemini 1.5 Flash language model
- **User_Profile**: Demographic data including age, sex, weight (kg), height (cm), and fitness goal
- **Exercise_Hit**: Retrieved exercise document with name, category, muscles, equipment, difficulty, kcal_per_min, and embedding
- **Recipe_Hit**: Retrieved recipe document with name, calories, protein_g, carbs_g, fat_g, ingredients, tags, and embedding
- **RAG_Pipeline**: Retrieval-Augmented Generation pipeline that embeds queries, retrieves context, and generates responses
- **Ingestion_Script**: Python script that crawls, embeds, normalizes, and indexes data into Elasticsearch
- **Frontend**: Next.js 14 App Router application deployed on Vercel
- **API_Route**: Next.js API endpoint handling requests and responses
- **SSE**: Server-Sent Events protocol for streaming LLM tokens to the client
- **Query_Embedding**: 384-dimensional dense vector representation of user query
- **Weekly_Plan**: Personalized fitness and nutrition schedule generated by the LLM

## Requirements

### Requirement 1: User Profile Input

**User Story:** As a User, I want to enter my demographic information and fitness goal, so that I can receive personalized recommendations.

#### Acceptance Criteria

1. THE Frontend SHALL display input fields for age, sex, weight (kg), height (cm), and natural-language goal
2. WHEN the User submits the form, THE Frontend SHALL validate that all fields contain non-empty values
3. WHEN validation fails, THE Frontend SHALL display error messages indicating which fields are invalid
4. WHEN validation succeeds, THE Frontend SHALL send the User_Profile to the API_Route

### Requirement 2: Query Embedding Generation

**User Story:** As a System, I want to convert user queries into vector embeddings, so that I can perform semantic search.

#### Acceptance Criteria

1. WHEN the API_Route receives a User_Profile, THE Embedding_Model SHALL generate a Query_Embedding from the goal text
2. THE Query_Embedding SHALL be a 384-dimensional dense vector
3. WHEN embedding generation fails, THE System SHALL return an error response with status code 500
4. THE Embedding_Model SHALL execute in the Node.js runtime without external API calls

### Requirement 3: Vector Search Retrieval

**User Story:** As a System, I want to retrieve semantically relevant exercises and recipes, so that I can provide contextually appropriate recommendations.

#### Acceptance Criteria

1. WHEN a Query_Embedding is generated, THE System SHALL perform k-NN search against the exercises_v1 index
2. WHEN a Query_Embedding is generated, THE System SHALL perform k-NN search against the recipes_v1 index
3. THE System SHALL retrieve the top 5 Exercise_Hit documents using cosine similarity
4. THE System SHALL retrieve the top 5 Recipe_Hit documents using cosine similarity
5. WHEN the Vector_Store is unreachable, THE System SHALL return an error response with status code 503

### Requirement 4: LLM Response Generation

**User Story:** As a System, I want to generate personalized weekly plans based on retrieved context, so that I can provide actionable recommendations.

#### Acceptance Criteria

1. WHEN Exercise_Hit and Recipe_Hit documents are retrieved, THE System SHALL construct a prompt containing User_Profile and retrieved context
2. THE System SHALL send the prompt to the LLM
3. THE LLM SHALL generate a Weekly_Plan grounded in the retrieved Exercise_Hit and Recipe_Hit documents
4. WHEN the LLM is unavailable, THE System SHALL return an error response with status code 503
5. THE System SHALL NOT include information not present in the retrieved context

### Requirement 5: Streaming Response Delivery

**User Story:** As a User, I want to see the plan being generated in real-time, so that I receive immediate feedback.

#### Acceptance Criteria

1. WHEN the LLM generates tokens, THE API_Route SHALL stream tokens to the Frontend using SSE
2. THE Frontend SHALL display tokens incrementally as they arrive
3. WHEN the stream completes, THE Frontend SHALL display the complete Weekly_Plan
4. WHEN the stream is interrupted, THE Frontend SHALL display an error message

### Requirement 6: Exercise Data Ingestion

**User Story:** As a System Administrator, I want to populate the exercise database, so that the System can retrieve exercise recommendations.

#### Acceptance Criteria

1. THE Ingestion_Script SHALL fetch exercise data from the Wger Workout Manager API
2. THE Ingestion_Script SHALL generate embeddings for each exercise using the Embedding_Model
3. THE Ingestion_Script SHALL normalize exercise data to include name, category, muscles, equipment, difficulty, and kcal_per_min
4. THE Ingestion_Script SHALL bulk index exercise documents into the exercises_v1 index with 384-dimensional dense_vector fields
5. THE exercises_v1 index SHALL use cosine similarity for vector search

### Requirement 7: Recipe Data Ingestion

**User Story:** As a System Administrator, I want to populate the recipe database, so that the System can retrieve nutrition recommendations.

#### Acceptance Criteria

1. THE Ingestion_Script SHALL scrape recipe data from Allrecipes.com using Schema.org JSON-LD extraction
2. THE Ingestion_Script SHALL generate embeddings for each recipe using the Embedding_Model
3. THE Ingestion_Script SHALL normalize recipe data to include name, calories, protein_g, carbs_g, fat_g, ingredients, and tags
4. THE Ingestion_Script SHALL bulk index recipe documents into the recipes_v1 index with 384-dimensional dense_vector fields
5. THE recipes_v1 index SHALL use cosine similarity for vector search

### Requirement 8: Elasticsearch Index Configuration

**User Story:** As a System Administrator, I want properly configured vector indices, so that semantic search performs correctly.

#### Acceptance Criteria

1. THE exercises_v1 index SHALL define a dense_vector field with 384 dimensions
2. THE recipes_v1 index SHALL define a dense_vector field with 384 dimensions
3. THE dense_vector fields SHALL use cosine similarity as the distance metric
4. THE indices SHALL support k-NN search queries
5. WHEN an index does not exist, THE Ingestion_Script SHALL create it with the correct mapping

### Requirement 9: Deployment and Availability

**User Story:** As a User, I want the application to be available 24/7 for 2 weeks, so that I can access it at any time.

#### Acceptance Criteria

1. THE Frontend SHALL be deployed on Vercel free tier
2. THE Vector_Store SHALL be hosted on Elastic Cloud 14-day trial
3. THE System SHALL support 20 concurrent users
4. THE System SHALL remain available for 14 consecutive days
5. WHEN the Elastic Cloud trial expires, THE System SHALL return an error response indicating service unavailability

### Requirement 10: API Key Management

**User Story:** As a System Administrator, I want to securely manage API keys, so that external services remain accessible.

#### Acceptance Criteria

1. THE System SHALL store the Elasticsearch API key in environment variables
2. THE System SHALL store the Google Gemini API key in environment variables
3. THE System SHALL NOT expose API keys in client-side code
4. THE System SHALL NOT commit API keys to version control
5. WHEN an API key is invalid, THE System SHALL return an error response with status code 401

### Requirement 11: Error Handling and User Feedback

**User Story:** As a User, I want clear error messages when something goes wrong, so that I understand what happened.

#### Acceptance Criteria

1. WHEN the Vector_Store is unreachable, THE Frontend SHALL display a message indicating search service unavailability
2. WHEN the LLM is unavailable, THE Frontend SHALL display a message indicating generation service unavailability
3. WHEN embedding generation fails, THE Frontend SHALL display a message indicating processing error
4. WHEN network errors occur, THE Frontend SHALL display a message indicating connection failure
5. THE error messages SHALL NOT expose internal system details or API keys

### Requirement 12: Response Time Performance

**User Story:** As a User, I want to receive recommendations quickly, so that I have a responsive experience.

#### Acceptance Criteria

1. WHEN a User_Profile is submitted, THE System SHALL return the first LLM token within 5 seconds
2. THE k-NN search against exercises_v1 SHALL complete within 1 second
3. THE k-NN search against recipes_v1 SHALL complete within 1 second
4. THE Query_Embedding generation SHALL complete within 500 milliseconds
5. WHEN performance thresholds are exceeded, THE System SHALL still complete the request without timeout

### Requirement 13: Data Ingestion Performance

**User Story:** As a System Administrator, I want efficient data ingestion, so that I can populate the database quickly.

#### Acceptance Criteria

1. THE Ingestion_Script SHALL use bulk indexing with batch sizes of at least 100 documents
2. THE Ingestion_Script SHALL log progress every 100 documents processed
3. WHEN ingestion fails for a document, THE Ingestion_Script SHALL log the error and continue processing
4. THE Ingestion_Script SHALL complete exercise ingestion within 10 minutes for 1000 exercises
5. THE Ingestion_Script SHALL complete recipe ingestion within 30 minutes for 5000 recipes

### Requirement 14: Frontend User Interface

**User Story:** As a User, I want an intuitive interface, so that I can easily interact with the System.

#### Acceptance Criteria

1. THE Frontend SHALL display a form component for User_Profile input
2. THE Frontend SHALL display a component for streaming Weekly_Plan output
3. THE Frontend SHALL display loading indicators during processing
4. THE Frontend SHALL use responsive design supporting mobile and desktop viewports
5. THE Frontend SHALL provide visual feedback for form validation errors

### Requirement 15: Repository Structure and Organization

**User Story:** As a Developer, I want a well-organized codebase, so that I can navigate and maintain the System.

#### Acceptance Criteria

1. THE repository SHALL contain an app/ directory for Next.js pages and API routes
2. THE repository SHALL contain a components/ directory for React components
3. THE repository SHALL contain a lib/ directory for Elasticsearch, embedding, LLM, and prompt utilities
4. THE repository SHALL contain a scripts/ directory for Python ingestion scripts
5. THE repository SHALL contain a types/ directory for TypeScript interfaces
